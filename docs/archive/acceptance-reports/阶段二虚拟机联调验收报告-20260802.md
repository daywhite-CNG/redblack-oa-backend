## 1. 验收范围

本次验收覆盖以下真实运行组件：

- Nginx 同源入口；
- `gateway-service`；
- `identity-service`；
- MySQL 8.4；
- Redis 7.4；
- Kafka 3.9.1（KRaft）；
- 身份、组织、角色、菜单、权限缓存、幂等与 Outbox 相关接口。

`approval-service`、`office-service`、`audit-service` 当前仍是拒绝未实现接口的安全骨架，不在本次“通过”范围内。

## 3. 验收结果

### 3.1 真实基础设施冒烟

执行：

```bash
./deploy/verify-phase2.sh
```

结果：通过。

- 6 个容器全部为 `healthy`；
- Flyway 成功迁移 3 条，3 个演示账号存在；
- Redis 读写往返成功；
- 使用 `edenhill/kcat:1.7.1` 完成 Kafka 确认式生产与消费；
- 管理员经 Nginx → Gateway → Identity 登录和鉴权成功；
- 普通员工调用用户管理接口返回 403；
- 管理员退出后原令牌再次访问返回 401。

### 3.2 身份与 RBAC API

执行：

```bash
python3 ./deploy/verify-identity-api.py http://127.0.0.1/api/v1
```

结果：`Identity API acceptance passed: 35/35 public operations exercised.`

覆盖内容包括：

- 登录、退出、当前用户、个人资料和密码修改；
- 用户、部门、角色、权限和菜单的查询及写操作；
- 部门领导数据范围；
- 普通员工越权拒绝和范围外对象隐藏；
- UUID 格式 `Idempotency-Key`；
- 幂等结果重放前重新鉴权；
- 临时用户、部门、角色和菜单的自动清理。

### 3.3 Redis 与 Kafka 韧性

执行：

```bash
./deploy/verify-phase2-resilience.sh
```

结果：通过。

- 清空 Redis 后，管理员授权查询从 MySQL 回源成功，并重新建立权限缓存；
- Kafka 停止期间，登录事务仍返回成功，审计 Outbox 以 `PENDING` 状态保存在 MySQL；
- Kafka 恢复后，同一 Outbox 事件转为 `SENT` 并可从审计主题消费；
- 本轮恢复事件 ID：`823e1ac4-a3de-4692-b4bf-d8ce5262d503`；
- 故障恢复期间观察到重复投递，符合项目声明的“至少一次”语义，消费者仍必须按 `eventId` 去重。

### 3.4 整机重启与数据持久性

通过 VMware Tools 对虚拟机执行软关机并重新启动，随后重新执行 3.1 和 3.2，均再次通过。

重启后结果：

- 地址仍为 `192.168.12.131`；
- SSH、Docker 和 6 个 Compose 容器自动恢复；
- 3 条 Flyway 迁移和 3 个演示账号保持；
- 临时用户、角色、部门、菜单数量均为 0；
- Outbox 最终状态为 `SENT=110`，无 `PENDING` 或 `SENDING` 遗留；
- 3306、6379、9092、8080 仍未对宿主机开放。

## 6. 验收边界与下一阶段

本报告只将阶段二标记为通过。以下能力尚未形成真实后端闭环，因此 Red&Black OA V1 仍不能标记为全部完成：

- 请假申请、提交、审批、驳回、转交、撤回和历史记录；
- 公告、通知、工作台读模型；
- OSS 私有附件上传、下载、删除和对象级权限；
- 审计消费者、重复消息去重和死信重放；
- 前端从 Mock 切换为真实 API 后的三角色端到端验收。

下一阶段应先实现并验收 `approval-service`，再推进 `office-service`、`audit-service` 和前端真实接口闭环。
