# Red&Black OA V2 HTTP、内部服务与事件接口契约

> 更新日期：2026-09-18  
> 状态：毕业设计目标契约；当前已实现端点与新增联盟链端点需按版本逐步落地  
> 关联文档：`产品需求文档.md`、`权限设计.md`

## 1. 契约目标

本文定义浏览器 HTTP、服务间同步调用、Kafka 事件和联盟链证据模型。任何实现变更遵循“先修改契约、确认影响范围、再修改代码和测试”的顺序。

现有 OpenAPI 文件仍是 V1 当前快照；V2 实现开始前必须同步升级，不得用本文描述掩盖尚未实现的接口。

## 2. 版本与兼容性

- 外部 HTTP 前缀保持 `/api/v1`，新增联盟链资源位于 `/api/v1/blockchain/**`。
- 破坏性字段变化必须升级路径版本或提供明确迁移窗口。
- Kafka 主题和事件类型带版本；消费者忽略未知可选字段，但不得猜测未知动作。
- 证据规范化使用独立 `payloadSchemaVersion`，历史证据始终按原版本验真。
- 本文中的区块链端点属于 V2 目标；只有代码、测试和真实运行验证后才能标记为已实现。

## 3. 通用传输规范

### 3.1 请求头

| 请求头 | 必填 | 说明 |
|---|---:|---|
| `Authorization: Bearer <token>` | 是，登录接口除外 | 用户访问令牌 |
| `X-Request-Id` | 否 | 客户端链路 ID；缺失时网关生成 |
| `Idempotency-Key` | 写接口按约定 | 防止网络重试造成重复业务 |
| `If-Match` | 更新/审批接口 | 资源版本，格式为整数或 ETag |

客户端不得发送可信身份头；网关必须移除外部 `X-User-Id`、`X-Roles`、`X-Permissions` 等伪造字段。

### 3.2 时间、ID与摘要

- 时间使用 ISO 8601，接口返回带时区的 UTC 或明确约定的时间字符串。
- 数据库 ID 在 JSON 中按现有契约统一处理，前端不得因 JavaScript 精度丢失长整型。
- SHA-256 表示为小写十六进制，并在资源中同时返回 `hashAlgorithm: "SHA-256"`。
- 交易哈希、合约地址保持链 SDK 的规范格式。
- 分页从 1 开始，默认 `page=1&size=20`，`size` 最大值由服务端限制。

{
  "code": "OK",
  "message": "success",
  "data": {},
  "requestId": "01J...",
  "timestamp": "2026-09-18T02:30:00Z"

### 3.6 HTTP 状态码

| 状态码 | 语义 |
|---:|---|
| 200 | 查询或幂等操作成功 |
| 201 | 资源创建成功 |
| 202 | 异步任务已接受，尚未完成 |
| 204 | 无响应体成功 |
| 400 | 参数或业务前置条件错误 |
| 401 | 未认证或会话失效 |
| 403 | 已认证但无操作权限 |
| 404 | 资源不存在，或出于隐私隐藏其存在性 |
| 409 | 状态冲突、重复资源或乐观锁冲突 |
| 422 | 语义校验失败 |
| 503 | 依赖服务或联盟链不可用 |

## 6. 关键 OA 请求

### 6.1 创建草稿

```http
POST /api/v1/leave-applications
Idempotency-Key: 4f95...
```

```json
{
  "leaveType": "ANNUAL",
  "startTime": "2026-09-21T01:00:00Z",
  "endTime": "2026-09-21T10:00:00Z",
  "reason": "个人事务",
  "attachmentIds": [101]
}
```

响应创建 `DRAFT`，不产生链上证据。

### 6.2 提交或重新提交

```http
POST /api/v1/leave-applications/10001/submit
Idempotency-Key: 63ae...
If-Match: 4
```

```json
{
  "comment": null
}
```

业务响应只确认 OA 事务是否成功：

```json
{
  "applicationId": 10001,
  "status": "PENDING",
  "submissionRound": 2,
  "evidence": {
    "evidenceId": "EV-20260918-0001",
    "action": "RESUBMIT",
    "anchorStatus": "PENDING"
  },
  "version": 5
}
```

`anchorStatus=PENDING` 不能表述为已上链。

### 6.3 审批动作

同意示例：

```http
POST /api/v1/approval-tasks/9001/approve
Idempotency-Key: 0d63...
If-Match: 2
```

```json
{
  "comment": "同意"
}
```

驳回和转交分别使用 `/reject`、`/transfer`；转交请求包含 `targetUserId` 和可选原因。审批意见保存在链下，不进入链上负载。

### 7.4 验真

```http
POST /api/v1/blockchain/verifications
Idempotency-Key: 36cb...
```

使用服务器快照：

```json
{
  "evidenceId": "EV-20260918-0001",
  "mode": "SERVER_SNAPSHOT"
}
```

附加本地文件摘要：

```json
{
  "evidenceId": "EV-20260918-0001",
  "mode": "FILE_DIGESTS",
  "attachmentDigests": [
    {
      "fileId": 101,
      "sha256": "f34a...",
      "sizeBytes": 58231
    }
  ]
}
```

浏览器只提交摘要，不上传验真文件原文。

响应：

```json
{
  "verificationId": "VER-20260918-0001",
  "evidenceId": "EV-20260918-0001",
  "result": "MATCH",
  "storedHash": "8d4a...",
  "calculatedHash": "8d4a...",
  "transactionHash": "0x...",
  "blockNumber": 128,
  "verifiedAt": "2026-09-18T02:30:00Z"
}
```

### 7.5 失败重试

```http
POST /api/v1/blockchain/evidences/EV-20260918-0001/retry
Idempotency-Key: d0d2...
```

```json
{
  "reason": "联盟链网络恢复后人工补偿"
}
```

成功接受返回 202 和原证据 ID。服务必须先查链；若链上已存在，则补录回执而不是发送重复交易。

### 7.6 网络状态

响应只返回运行状态、区块高度、组织标识、节点标识、SDK连通和最近更新时间。不得返回私钥路径、证书正文、宿主机口令或可用于攻击的内部凭据。

## 8. 资源模型

### 8.1 `ChainEvidence`

| 字段 | 类型 | 说明 |
|---|---|---|
| `evidenceId` | string | 证据唯一 ID |
| `sourceEventId` | string | 源事件唯一 ID |

| `evidenceHash` | string | 证据摘要 |
| `previousEvidenceHash` | string/null | 前序摘要 |
| `attachmentHashRoot` | string/null | 附件摘要根 |
| `organizationId` | string | 写入组织 |
| `transactionHash` | string/null | 交易哈希 |
| `blockNumber` | long/null | 区块高度 |
| `failureCode` | string/null | 脱敏失败码 |
| `occurredAt` | datetime | 业务发生时间 |
| `submittedAt` | datetime/null | 交易提交时间 |
| `confirmedAt` | datetime/null | 区块确认时间 |

### 8.2 `EvidenceFileMetadata`

内部证据快照使用：

```json
{
  "fileId": 101,
  "sha256": "f34a...",
  "sizeBytes": 58231,
  "status": "AVAILABLE"
}
```

文件名、contentType 和 objectKey 不参与链上负载；是否参与规范化由 schemaVersion 明确。

## 9. 服务间同步接口

内部接口必须使用短时内部服务令牌，并校验调用方服务身份。

### 9.1 身份服务

- 查询用户有效性、部门、权限快照和授权版本。
- 根据用户 ID 批量查询必要的脱敏展示信息。

### 9.2 文件证据元数据

```http
GET /internal/v1/files/evidence-metadata?applicationId=10001&submissionRound=2
```

返回当前轮次不可变的附件 ID、SHA-256、大小和状态。现有只返回文件名、类型、大小的元数据接口不足以支持证据计算，必须扩展或以 `FILE_EVIDENCE_SNAPSHOT` 事件替代。

### 9.3 区块链服务

正常存证只允许由 Kafka 证据事件触发，不提供任意内部 `createEvidence(payload)` 接口。内部健康检查和部署探针不返回业务数据。

## 10. 事件契约

### 10.1 主题

| 主题 | 生产者 | 消费者 | 用途 |
|---|---|---|---|
| `redblack.identity.events.v1` | identity | 相关服务 | 身份和授权变化 |
| `redblack.approval.events.v1` | approval | office 等 | 业务投影和通知 |
| `redblack.audit.events.v1` | 各业务服务 | audit | 操作日志 |
| `redblack.blockchain.evidence.v1` | approval | blockchain | 可信审批证据 |

链服务不得把 `redblack.audit.events.v1` 当作审批事实源。

### 10.2 统一事件信封

```json
{
  "eventId": "uuid",
  "eventType": "EvidenceRequested",
  "eventVersion": 1,
  "occurredAt": "2026-09-18T02:20:00Z",
  "producer": "approval-service",
  "aggregateType": "LEAVE_APPLICATION",
  "aggregateId": "10001",
  "requestId": "01J...",
  "traceId": "...",
  "actor": {
    "subjectHash": "a12b..."
  },
  "payload": {}
}
```

### 10.3 `EvidenceRequested` v1

```json
{
  "sourceEventId": "uuid",
  "evidenceId": "EV-20260918-0001",
  "schemaVersion": 1,
  "businessType": "LEAVE_APPLICATION",
  "applicationId": 10001,
  "submissionRound": 2,
  "action": "RESUBMIT",
  "fromStatus": "REJECTED",
  "toStatus": "PENDING",
  "operatorSubjectHash": "a12b...",
  "organizationId": "OrgEnterprise",
  "occurredAt": "2026-09-18T02:20:00Z",
  "businessVersion": 5,
  "attachmentHashRoot": "113f...",
  "previousEvidenceHash": "4a31..."
}
```

禁止加入姓名、部门名称、请假原因、审批意见、文件名和对象存储地址。

### 10.4 发布与消费语义

- 业务变更和 Outbox 同事务提交。
- 生产者至少一次发布。
- 同一申请使用稳定 Kafka Key 保序。
- 消费者以 `eventId/sourceEventId` 建立 Inbox 幂等。
- 不认识的动作或 schemaVersion 进入隔离状态，不猜测处理。
- 处理失败保留错误码和下一次尝试时间；超过策略进入人工处理，不丢弃事件。

## 11. 规范化与哈希契约

### 11.1 基本规则

- 使用明确的字段白名单和固定字段顺序。
- 字符串使用 UTF-8；时间规范化为 UTC。
- `null`、空字符串和字段缺失的语义必须由 schemaVersion 固定。
- 数字禁止因语言差异产生科学计数法或精度变化。
- 规范化输出不得包含展示名称和可变字段。
- 哈希输入增加业务域分离标识，避免跨类型重放。

### 11.2 附件哈希根

首个实现必须在 POC 后从以下方案中固定一种，并记录到 schemaVersion：

1. 按稳定 fileId 排序的版本化有序聚合哈希。
2. 明确定义叶子、排序和奇数节点规则的 Merkle Root。

不得只写“计算附件哈希”而不定义算法。

## 12. 幂等、并发与恢复

- HTTP 写请求使用 `Idempotency-Key`。
- 业务更新使用 `If-Match` 或版本字段。
- `chain_inbox_event.event_id` 唯一。
- `chain_evidence.source_event_id` 和 `evidence_id` 唯一。
- 合约拒绝重复 `evidenceId`。
- 回执未知保持 `SUBMITTED`，查询链后决定补录或重发。
- 重试使用原证据标识和原规范化负载。
- 同一申请后续证据必须等待前序证据达到可确定状态。

## 14. 契约验收清单

1. 文档、OpenAPI、前端类型和后端 DTO 字段一致。
2. 提交与重新提交在证据事件中区分 `SUBMIT` 和 `RESUBMIT`。
3. 证据事件含起止状态、轮次和附件哈希根，不含敏感明文。
4. 文件证据元数据能够提供稳定 SHA-256 快照。
5. 重复 HTTP 请求和重复 Kafka 事件均不产生重复业务或链上记录。
6. 业务接口返回 `PENDING` 时不宣称已经上链。
7. 验真结果能覆盖一致、不一致、不存在、待确认和网络不可用。
8. 交易回执未知时先查链再重试。
9. 无权限用户不能通过证据 ID 或交易哈希读取业务。
10. 网关路由、权限种子、菜单、服务端鉴权和前端页面同步更新。
11. Java 21 与目标链 SDK 完成 POC 后再固化依赖版本。
12. 所有新增端点有正常、边界、异常和权限测试。
