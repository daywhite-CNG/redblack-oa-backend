## 1. 文档目的

本文定义 Red&Black OA 毕业设计版本的产品范围、领域模型、业务规则、联盟链能力、服务边界和验收标准，作为前端、后端、智能合约、部署与论文实验的统一依据。

本版本在保留现有 OA 能力的基础上，将联盟链提升为核心技术主线。OA 是产生可信业务事实的应用场景，联盟链负责关键审批事实的存证、追溯和验真，二者不得混为一体。

## 2. 项目背景与产品定位

### 2.1 产品定位

Red&Black OA 是面向小型企业的协同办公系统，以请假审批作为首个完整业务场景，引入联盟链实现审批关键事实的可信存证、防篡改验证和全过程追溯。

系统采用链上链下协同架构：

- 员工、部门、请假理由、审批意见和附件原文保存在企业数据库或对象存储中。
- 正式审批动作、状态迁移、附件摘要和证据前后关系经过规范化后写入联盟链。
- OA 数据库是业务事实源；联盟链是证据确认源。
- 操作日志用于系统审计，链上证据用于独立验真，两者不能互相替代。

### 2.2 毕设技术重点

毕设重点不是“给 OA 增加区块链页面”，而是完成以下可信证据闭环：

```text
审批事实产生
→ 事务内生成证据事件
→ Kafka 异步传递
→ 规范化与哈希计算
→ 智能合约校验和登记
→ 交易回执落库
→ 链上链下独立验真
→ 故障恢复与实验验证
```

### 2.3 产品目标

1. 完成登录、组织权限、请假申请、审批、公告、消息、附件和操作日志等 OA 基础闭环。
2. 对提交、重新提交、同意、驳回、转交和撤回等正式动作形成不可变证据。
3. 通过智能合约校验证据唯一性、联盟组织写权限、状态迁移和前序证据关系。
4. 支持根据链下快照重新计算摘要，并与链上证据进行独立比对。
5. 区块链网络异常时不回滚已经成功的 OA 业务事务。
6. 网络恢复后安全补偿，避免重复写入或证据顺序错乱。
7. 确保链上不出现姓名、请假理由、审批意见、附件原文等敏感明文。
8. 形成可复现的部署、交易、篡改验证、幂等和节点故障实验材料。

### 2.4 成功标准

- 用户可完成请假审批完整流程，权限和数据范围符合设计。
- 每个正式审批动作均可追踪到证据事件、存证记录、交易哈希和区块高度。
- 重复事件不会产生重复链上证据。
- 修改链下业务快照或附件摘要后，验真能够返回不一致。
- 链网络停机时 OA 仍可完成审批，恢复后可完成补偿存证。
- 未授权用户无法查看、验证或重试不属于其权限范围的证据。
- 合约拒绝重复证据、无权限组织、错误前序哈希和非法状态迁移。
- 链上数据检查不包含产品规定的敏感明文字段。

### 3.1 P0：必须完成

#### OA 业务

- 工作台、通知和操作日志。

#### 联盟链

- 两个逻辑联盟组织及多节点实验网络。
- 审批证据专用事件契约。
- 独立 `blockchain-service`。
- `ApprovalEvidenceRegistry` 智能合约。
- 审批证据异步上链、回执保存和时间线查询。
- 数据库与合约双重幂等。
- 业务快照和附件摘要验真。
- 网络状态查询与受控失败重试。
- 链中断、重复事件、回执未知和数据篡改实验。

### 3.2 P1：应完成

- 公告发布、编辑、撤回和阅读状态。
- 联盟链概览页。
- 合约部署信息和联盟组织只读页面。
- 验真历史与结果导出。
- 轻量 `OrganizationRegistry` 合约；仅在 P0 完成后实施。

### 3.3 本期不做

- 完整多租户 SaaS 和跨企业业务协作。
- 将数据库、附件原文或审批意见全文上链。
- 为每名 OA 用户创建和托管链上私钥。
- 公链代币、NFT、挖矿、钱包支付和经济激励。
- 动态节点运维平台、在线签发证书和前端部署合约。
- 复杂投票治理、隐私计算、跨链和零知识证明。
- 覆盖所有 OA 业务类型的通用存证平台。
- 把草稿保存、登录、页面浏览、通知已读等普通操作写入联盟链。

## 4. 领域术语

| 术语 | 定义 |
|---|---|
| OA 部门 | 企业内部的行政组织，用于审批流转和数据范围控制。 |
| 联盟组织 | 参与联盟链治理、节点运行和交易签名的主体，不等同于 OA 部门或租户。 |
| 审批事实 | 请假申请发生的一次正式业务动作及状态变化。 |
| 证据事件 | 在审批事务内产生、用于驱动存证的不可变事件。 |
| 规范化负载 | 按指定 schemaVersion、字段白名单和顺序生成的确定性证据内容。 |
| 证据哈希 | 规范化负载按指定算法计算出的摘要。 |
| 附件哈希根 | 当前提交轮次已绑定可用附件摘要集合的确定性聚合结果。 |
| 前序证据哈希 | 同一申请上一条正式证据的哈希，用于建立证据链。 |
| 存证任务 | `blockchain-service` 对一条证据事件的接收、提交和确认过程。 |
| 链上确认 | 交易成功进入区块并取得可验证回执。 |
| 验真 | 重新计算链下摘要并与智能合约记录进行比对。 |
| 操作日志 | 面向系统审计的用户操作记录，不作为审批证据事实源。 |

## 5. 用户、角色与联盟组织

### 5.1 OA 角色

| 角色 | 主要职责 |
|---|---|
| 系统管理员 | 管理用户、部门、角色、菜单和全局业务数据；不接触链私钥。 |
| 部门领导 | 查看管辖范围申请并执行审批。 |
| 普通员工 | 管理本人申请、查看本人证据和通知。 |

### 5.2 联盟链角色

| 角色 | 主要职责 | 明确限制 |
|---|---|---|
| 存证审计员 | 查看授权证据、执行验真、导出验真结果 | 不审批、不修改 OA 数据、不重试交易 |
| 联盟链运维员 | 查看网络和合约状态、处理失败存证 | 不修改业务、不提交任意哈希、不查看无权限业务详情 |

### 5.3 联盟组织

首期逻辑组织：

- `OrgEnterprise`：企业组织，产生并提交审批证据。
- `OrgAudit`：审计组织，参与共识并提供独立验证能力。

OA 用户由组织级服务账户代签交易，用户身份仅以不可逆主体摘要进入证据。联盟组织不是为现有 OA 增加多租户模型。

## 7. 核心业务旅程

### 7.1 请假审批

1. 员工创建草稿并上传附件。
2. 员工提交申请，系统校验字段、附件状态和乐观锁版本。
3. 申请进入 `PENDING`，生成审批任务和 `SUBMIT` 证据事件。
4. 部门领导执行同意、驳回或转交。
5. 系统更新申请、任务和审批记录，并产生对应证据事件。
6. 员工可以在允许状态下撤回，或在驳回后编辑并重新提交。

### 7.2 异步存证

1. `approval-service` 在业务事务内写入证据 Outbox。
2. 发布器将事件发送到区块链专用 Kafka 主题。
3. `blockchain-service` 使用 Inbox 按 `sourceEventId` 幂等消费。
4. 服务生成版本化规范负载并计算证据哈希。
5. 服务调用合约，保存交易哈希、区块高度和确认时间。
6. 前端分别显示业务状态与存证状态。

### 7.3 独立验真

1. 有权限用户选择证据或申请。
2. 系统读取对应的不可变链下快照。
3. 按证据记录中的 schemaVersion 重新规范化并计算摘要。
4. 查询合约中的证据。
5. 比对证据哈希、前序哈希和附件哈希根。
6. 返回验真结果，不改变审批业务状态。

### 7.4 故障恢复

1. 链不可用时，OA 事务正常完成，存证记录进入 `PENDING` 或 `FAILED`。
2. 交易已提交但回执未知时保持 `SUBMITTED`。
3. 重试前先按 `evidenceId` 查询合约。
4. 链上已存在时补录回执；不存在时才使用原 `sourceEventId` 重试。
5. 恢复过程不得改变原始规范化负载。

## 8. 状态模型

### 8.1 请假申请状态

```text
DRAFT → PENDING → APPROVED
              └→ REJECTED → PENDING
         └───────────────→ WITHDRAWN
```

现有业务状态保持：`DRAFT`、`PENDING`、`APPROVED`、`REJECTED`、`WITHDRAWN`。

### 8.2 正式证据动作

- `SUBMIT`
- `RESUBMIT`
- `APPROVE`
- `REJECT`
- `TRANSFER`
- `WITHDRAW`

重新提交必须是独立动作 `RESUBMIT`，不得继续以普通 `SUBMIT` 表达。

### 8.3 存证状态

| 状态 | 含义 |
|---|---|
| `PENDING` | 证据已生成，等待提交交易。 |
| `SUBMITTED` | 交易已提交，回执尚未确定。 |
| `CONFIRMED` | 交易已经区块确认。 |
| `FAILED` | 明确失败，等待人工或自动补偿。 |

合法恢复：`FAILED → PENDING`。回执未知时不能直接进入 `FAILED` 后盲目重发。

### 8.4 验真结果

- `MATCH`：链上链下一致。
- `MISMATCH`：重新计算结果与链上不一致。
- `NOT_FOUND`：链上不存在该证据。
- `PENDING`：尚未确认，暂不能完成验真。
- `UNAVAILABLE`：联盟链暂不可访问。

## 9. OA 功能需求

### 9.1 身份、组织与权限

- 支持登录、退出、当前用户、密码修改和会话失效。
- 支持用户、部门、角色、菜单和权限维护。
- 权限由菜单、操作、接口、数据范围和对象级规则共同决定。
- 权限事实源为 `identity-service`，其他服务不得自行创造角色语义。

### 9.2 请假申请

- 草稿允许编辑和删除；提交后不得直接覆盖历史事实。
- 提交必须生成提交轮次，首轮为 1，驳回后重新提交递增。
- 同意、驳回、转交、撤回和重新提交必须记录审批记录。
- 每次写操作使用乐观锁；重复请求使用幂等键。
- 业务成功与链上确认分别反馈。

### 9.3 附件

- 文件上传后计算并保存 SHA-256。
- 仅状态为 `AVAILABLE` 且绑定当前申请的附件参与证据计算。
- 按稳定标识排序后计算当前轮次的 `attachmentHashRoot`。
- 已产生证据的附件快照不可修改；新轮次产生新的哈希根。
- 文件原文和对象存储地址不得上链。

### 9.4 公告、消息和工作台

- 保留现有公告发布、撤回、阅读和通知能力。
- 工作台增加本人待确认或失败存证数量，但不泄露他人数据。
- 存证成功、失败或恢复可产生通知，通知本身不上链。

### 9.5 操作日志

- 记录敏感管理操作、审批操作、验真和人工重试。
- 日志不能替代证据事件，也不能作为链上证据唯一来源。
- 日志不得记录私钥、证书内容、请假理由或完整规范化负载。

## 10. 联盟链功能需求

### 10.1 联盟链概览

展示 Chain ID、Group ID、共识类型、区块高度、组织数、节点数、在线节点数、今日存证量、成功率、待处理数、失败数、平均确认耗时、最近区块和最近证据。

网络状态统一为 `HEALTHY`、`DEGRADED`、`UNAVAILABLE`。

### 10.2 审批存证列表

筛选条件：申请编号、证据编号、动作、提交轮次、存证状态、验真结果、写入组织和时间范围。

关键字段：证据编号、申请编号、动作、轮次、证据哈希、交易哈希、区块高度、组织、发生时间、确认时间、存证状态和验真结果。

### 10.3 存证详情与时间线

详情分为：

1. 业务关联信息。
2. 规范化字段与哈希结构。
3. 合约地址、交易哈希和区块定位。
4. 验真结果和验证历史。

申请详情增加可信证据区，但仍以请假业务状态作为审批结果。

### 10.4 存证验真

- 支持使用服务器保存的不可变快照验真。
- 支持用户选择本地附件后由浏览器计算 SHA-256，仅提交摘要。
- 验真为只读操作，不产生新的业务状态或链上交易。
- 每次验真记录证据 ID、执行者、结果、时间和失败原因。

### 10.5 网络、合约和组织

- 网络页面只读显示节点、区块高度和连通状态。
- 合约页面只读显示名称、版本、地址、部署交易和部署区块。
- 组织页面只读显示组织标识、节点数和授权能力。
- 节点拓扑以部署配置为准，不开发通用节点管理 CRUD。

### 10.6 失败重试

- 仅联盟链运维员可以触发。
- 只有 `FAILED` 且满足补偿条件的记录可重试。
- 重试保持原 `sourceEventId`、`evidenceId` 和规范化负载。
- 重试前必须查询链上是否已经存在。
- 操作写入审计日志。

## 11. 链上链下数据边界

### 11.1 链上字段白名单

- `evidenceId`
- `sourceEventId`
- `businessType`
- `businessIdHash`
- `submissionRound`
- `action`
- `fromStatus`
- `toStatus`
- `operatorSubjectHash`
- `organizationId`
- `evidenceHash`
- `previousEvidenceHash`
- `attachmentHashRoot`
- `payloadSchemaVersion`
- `hashAlgorithm`
- `occurredAt`

### 11.2 禁止上链字段

- 姓名、部门名称、手机号等个人信息。
- 请假原因和审批意见。
- 文件名、对象存储地址和附件原文。
- JWT、内部服务令牌、私钥和证书内容。
- 数据库内部字段的完整明文映射。

### 11.3 密钥边界

- OA 用户不直接持有链私钥。
- `blockchain-service` 使用组织服务账户签名。
- 私钥和 SDK 证书通过只读 Secret 提供，不进入 Git、数据库、API 响应或日志。

## 12. 技术与服务边界

### 12.1 当前服务

- `gateway-service`：统一入口、认证前置检查、路由和限流边界。
- `identity-service`：身份、组织、RBAC 和权限事实源。
- `approval-service`：请假申请、任务、审批记录和业务状态机。
- `office-service`：工作台、公告、通知和附件。
- `audit-service`：操作日志投影与查询。
- `redblack-common`：稳定技术契约，不共享业务实体。

### 12.2 新增 blockchain-service

职责：

- 消费审批证据事件并通过 Inbox 幂等。
- 生成规范化负载和摘要。
- 维护证据前后关系和存证状态。
- 调用联盟链 SDK、提交交易和解析回执。
- 查询智能合约并执行验真。
- 处理回执未知、失败重试和补偿。
- 提供证据、网络、合约和组织查询接口。

独立数据库建议命名为 `redblack_blockchain`，不得复用 `audit-service` 数据库。

### 12.3 智能合约

P0 合约：`ApprovalEvidenceRegistry`。

必须支持：

- 登记证据。
- 防止重复 `evidenceId`。
- 校验写入组织。
- 校验前序证据哈希和合法状态迁移。
- 按证据 ID 查询。
- 按业务摘要查询时间线。
- 发出证据登记事件。

## 13. 事件、一致性与幂等

### 13.1 专用证据事件

主题建议为 `redblack.blockchain.evidence.v1`，事件类型为 `EvidenceRequested`。事件必须包含动作、起止状态、提交轮次、附件哈希根和前序证据哈希，且不得包含姓名、理由和审批意见。

### 13.2 一致性规则

- 业务事实和证据 Outbox 在同一数据库事务提交。
- 上链为异步过程，不纳入 OA 本地事务。
- 消费语义为至少一次，消费者必须幂等。
- 同一申请的证据使用稳定 Kafka Key 保序。
- 数据库 `unique(source_event_id)` 与合约唯一 `evidenceId` 形成双重幂等。
- 回执未知先查链，不得直接重复发送。

### 13.3 时间语义

- `occurredAt`：业务动作发生时间。
- `submittedAt`：交易提交时间。
- `confirmedAt`：交易进入区块并确认的时间。

三个时间不得互相替代。

## 14. 非功能需求

### 14.1 安全与隐私

- 所有外部接口经过网关认证，服务内再次做权限和对象级校验。
- 链上采用字段白名单，默认拒绝未定义字段。
- 未授权访问敏感证据时隐藏资源存在性。
- 合约校验组织身份和证据状态迁移。
- 密钥、证书和数据库凭据不得进入仓库。

### 14.2 可用性

- 链网络异常不阻塞 OA 审批。
- 存证失败有明确状态、原因、重试条件和审计记录。
- 降级状态不得伪装为链上成功。

### 14.3 可观测性

完整链路可关联：

```text
requestId → eventId → sourceEventId → evidenceId → transactionHash → blockNumber
```

指标至少包括待处理数、失败数、确认耗时、重试次数、当前区块高度、节点连通状态和验真结果分布。

### 14.4 性能

- OA 列表、详情和审批接口保持现有体验目标。
- 联盟链写入和验真的具体 P95 指标必须在 Java 21 SDK POC 后确定。
- 论文必须报告测试环境、样本量、并发量、成功率和延迟分位数，不能只报告平均值。

### 14.5 兼容性

- 后端以 Java 21 为硬约束。
- FISCO BCOS 和 Java SDK 的确切版本必须通过 POC 后固化。
- 历史证据必须根据自身 `payloadSchemaVersion` 验真。

## 15. 部署规划

推荐实验拓扑：

```text
OrgEnterprise：Node 1、Node 2
OrgAudit：Node 3、Node 4
```

推荐候选为 FISCO BCOS 3.x 与 PBFT 类共识，但在 POC 完成前不得标记为已验证版本。

- 四节点位于同一 VM 时，论文必须称“多组织仿真联盟链”。
- 两个组织分别位于两台 VM 时，可称“跨主机多组织联盟链实验环境”。
- 链节点端口仅在实验内网开放。
- 链节点部署与现有 OA Compose 分层管理。

## 16. 验收标准

### 16.1 OA 闭环

1. 普通员工只能管理本人申请。
2. 部门领导只能审批授权范围内的待办。
3. 管理员可维护组织、角色和菜单。
4. 乐观锁、幂等键和对象级权限真实生效。

### 16.2 存证闭环

1. 提交申请产生一条 `SUBMIT` 证据。
2. 驳回后重新提交产生 `RESUBMIT` 和新轮次。
3. 审批动作形成有序证据时间线。
4. 每条确认记录包含交易哈希、区块高度、合约地址和确认时间。
5. 同一事件重复投递只产生一条链上证据。

### 16.3 验真与隐私

1. 未修改数据返回 `MATCH`。
2. 修改业务快照或附件摘要返回 `MISMATCH`。
3. 不存在的证据返回 `NOT_FOUND`。
4. 检查链上原始交易，不出现禁止上链的敏感字段。
5. 无权限用户不能通过交易哈希绕过业务数据权限。

### 16.4 故障与恢复

1. 链停机期间 OA 审批仍成功。
2. 网络恢复后积压证据可补偿确认。
3. 回执超时时先查询链上状态，不产生重复交易。
4. 关闭一个节点后，在仍满足共识条件时网络继续出块。
5. 合约拒绝重复证据、错误前序哈希和未授权组织。

## 18. 已采用决策与待确认项

### 18.1 已采用决策

- 毕设只深挖请假审批全生命周期存证，不把所有 OA 功能区块链化。
- 单企业 OA 与联盟组织模型分离，不引入完整多租户改造。
- 新增独立 `blockchain-service`，不把链逻辑塞入 `audit-service`。
- OA 用户不直接托管链私钥，由组织服务账户签名。
- 文件原文和敏感业务字段不上链。
- OA 业务成功与链上确认异步解耦。

### 18.2 待 POC 后确认

- FISCO BCOS 和 Java SDK 确切版本及 Java 21 兼容性。
- 单 VM 仿真还是两台 VM 跨主机部署。
- 共识参数、节点数和端口规划。
- 附件哈希根采用 Merkle Root 还是版本化有序聚合哈希。
- 是否实施轻量 `OrganizationRegistry`。
- 性能目标、最大补偿时限和实验资源上限。
